# 提案要点与架构映射

本文件概括用户在本会话提供的提案，非原文逐字归档，也非独立文献审查。

候选问题是在显式子组通信存在时，从既有 ML kernel 恢复跨 lane 值依赖及输出归属，并在改变协作宽度时检查计算对象语义。检查目标包含运算、重复计数、成员/掩码坐标、临时存储、参与条件和写入者。

输入域与数值关系需要外部声明，且源程序在源语义下有效。数据格式中的量化分组 32 不应随线程协作宽度 32→64 改变。

候选贡献依次是关系恢复算法、不同执行组织之间的关系检查、由前两项约束的原生适配。至少前两项之一需要明确技术增量。agent 可作为候选生成方式，但不构成当前核心区别。

已有正确兼容模式是必要强基线。需要与 Polygeist、CKTI 在共同案例上比较具体能力，不能以其论文未使用某个术语断言不支持。也不能把 layout 表示、kernel/launch 联动或验证后搜索单独宣称首次提出。

重点风险是中间支持区域太小：简单模式已有方法足够，复杂模式又被 MVP 排除。应先验证真实融合 ML kernel 的差异，再扩大实现和基准规模。

架构据此分开 `analysis`、`verification`、`transforms`、`runtime` 和 `research`；benchmark 协议要求强基线、谱系留出、接受/错误放行双指标，以及人工关系/自动关系和既有变换/新增变换消融。
