# 以证据为门槛的路线图

本路线图不承诺六周完成，不预设 native64 优于 logical32。

| 阶段 | 交付 | 进入下一阶段的门槛 |
| --- | --- | --- |
| G0：仓库与协议 | 可运行参考路径、明确检查范围、回归测试 | CPU 检查通过；没有把模型结果当作 GPU 证明 |
| G1：差异验证 | 固定来源的真实案例、正确兼容基线、Polygeist/CKTI 逐例记录 | 至少一个共同适用案例显示值得研究的分析/检查需求，或明确需要调整问题 |
| G2：源码关系恢复 | 支持子集、来源可追踪的关系 IR、人工 oracle | 留出代码谱系上报告自动覆盖和拒绝原因；不能依赖逐 kernel 模板 |
| G3：关系检查 | 明确证明义务、负例、超时/未知、模型到代码边界 | 同时报告错误放行与有效接受；测试通过不代替关系保证 |
| G4：目标适配 | kernel/launch 联合变换、目标能力探测、已验证 fallback | 同一目标 GPU 上与正确兼容/人工参数化基线比较，有可测收益或解释清楚的失败 |
| G5：研究评估 | 谱系隔离的结果、关键消融、成本/性能原始记录 | 支持范围和主张一致；复现能追溯到原始工件 |

关键消融须保持后端和预算一致：人工正确关系 vs 自动恢复关系；相同关系下既有变换 vs 新增子组变换；相同候选与预算下普通测试 vs 结构检查加测试。

如果正确兼容模式已覆盖需求，且没有值得获得的性能或维护收益，应收窄或转向。如果普通 lowering 已能处理目标模式，应把工作准确定位为扩展，并重新评估技术贡献。
